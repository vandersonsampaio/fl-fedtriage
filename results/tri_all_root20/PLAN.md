# Plan — `tri_all` and the cosine signals at root 20, native and under FLTrust step parity

**Date:** 2026-11-19, written before any run. **Authorized by the author on 2026-11-19.** Descriptive, on development seeds 72–76; it confirms nothing, and seeds 62–71 are not touched. Extension of `results/tri_all_step_parity/PLAN.md`, which left root 20 out for cost ("It can follow if the reading at root 100 calls for it"). The author asked for it regardless of the root-100 reading.

## Why

The F3 confirmation (`results/f3_confirmation/`) reported H1′–H3′ at root 20 (`tri_all@r20` against the best single signal on the same root, `fltrust@r20` and `flame`). Root 20 is where the server update g₀ is noisiest, so it is where step parity can move the cosine signals the most. B1 ran only root 100, so on the VMs root 20 needs native runs as well as parity runs.

## Grid

- `tri_all`, `cos_bin`, `cosserver_only`, root 20, the 19 attack cells, seeds 72–76, `--log`, in two modes:
  - native (`--server_steps native`, the default) → `results/tri_all_root20/native/`;
  - parity (`--server_steps median`) → `results/tri_all_root20/parity/`.
- BloodMNIST 300 rounds, MNIST 150 rounds. 1,140 jobs (`jobs.txt`), generated by `scripts.triage_grid jobs --datasets <ds> --systems tri_all cos_bin cosserver_only --seeds 72 73 74 75 76 --rounds <300|150> --out results/tri_all_root20/<native|parity> --log --root_size 20 --server_steps <native|median>`, with the environment prefix removed. The cells are the same as in `results/tri_all_step_parity/jobs.txt` (checked by diff).
- `sr_bin` does not read g₀ or the root, so the B1 runs (`results/inclusion_mechanism/raw/`) serve as its reference in both modes.
- **Not included:** `fltrust@r20` on the VMs. `results/fltrust_parity/raw` has it at root 20 in both modes, run on the PC, so the contrast against it is cross-machine and only a rough reference, as at root 100.

## Contrasts

Per seed, mean over the 19 cells, CI95 with t, 5 seeds; BloodMNIST at H = 250 and H = 300, MNIST at H = 150. `@par` = parity, `@nat` = native, all at root 20.

1. S@par − S@nat for S in `tri_all`, `cos_bin`, `cosserver_only`.
2. `tri_all@par` − best single signal under parity (best by overall mean among `cos_bin@par`, `cosserver_only@par` and `sr_bin`, per dataset and horizon). Also reported against each of them.
3. The same contrast natively (`tri_all@nat` − best native signal).
4. Root sensitivity, per mode: S@r20 − S@r100, using `results/tri_all_step_parity/` (parity) and B1 (native) for root 100.

## Reading rule

The same rule as the root-100 plan, applied at root 20:

- **H1′ side (BloodMNIST, H = 250) is at risk** if either holds: (a) the CI95 of contrast 2 is not entirely above zero; (b) its mean is below half of contrast 3.
- **MNIST side (H = 150) is at risk** if the lower bound of the CI90 of `tri_all@par` − `cos_bin@par` is below −1 p.p.
- **At risk** → the root-20 claim is reported as dependent on the server step mode. **Not at risk** → it is reported with both versions.

## Descriptive, not part of the rule

- Contrasts by α, and per cell.
- Inclusion rates (Byzantine included, honest excluded), as in B1.
- `tri_all@r20` − `fltrust@r20` in each mode against `results/fltrust_parity/raw` (cross-machine).
- Late collapse with the D1 definition (MA10, 5 p.p.) on BloodMNIST up to 300 rounds.

## Execution

The same two VMs, environment and dispatcher as the root-100 grid (4 processes each, 1 thread per process, `OPENBLAS_CORETYPE=Haswell`, `ONEDNN_MAX_CPU_ISA=AVX2`). Odd lines on vm2, even on vm3. Each VM starts this grid only after the root-100 grid's `DISPATCH_END` appears in its own log, so the two never share the VM. Estimate from the root-100 timings: about 32 h.
